# POC: Automatic TLS from AKS cert-manager to Azure Application Gateway

## 1. Purpose

This POC publishes `https://gateway-rgs.eastus.cloudapp.azure.com` through Azure Application Gateway, Kong Gateway API, and AKS.

Certificate lifecycle:

```text
Let's Encrypt
  -> cert-manager Certificate
  -> Kubernetes TLS Secret: kong/gateway-rgs-tls-r
  -> External Secrets Operator PushSecret
  -> Azure Key Vault certificate: gateway-rgs-certs
  -> Application Gateway HTTPS listener
```

The PushSecret uses `cert/gateway-rgs-certs`. The `cert/` prefix is important because the Azure Key Vault provider imports the generated PKCS#12 value as a first-class Key Vault certificate. Using only `gateway-rgs-certs` creates a generic Key Vault secret instead.

Microsoft documentation: [TLS termination with Azure Key Vault certificates](https://learn.microsoft.com/en-us/azure/application-gateway/key-vault-certs?WT.mc_id=Portal-Microsoft_Azure_HybridNetworking#key-vault-azure-role-based-access-control-permission-model)

> Important: For an RBAC-enabled Key Vault, create the Application Gateway Key Vault certificate reference through Azure CLI, PowerShell, ARM, Bicep, or Terraform. Do not rely on the Azure portal certificate picker for the initial reference.

## 3. How many managed identities are required?

### Required for this TLS flow: two identities

1. **AKS/ESO writer identity**
   - Current identity: `azurekeyvaultsecretsprovider-rgs-gateway`
   - Client ID: `d5e0e47e-e878-4d12-b846-591b27035896`
   - Object ID: `32a694f3-4758-47e4-b52b-5beb0cc06903`
   - Purpose: External Secrets Operator writes the PFX generated from the Kubernetes TLS Secret into Key Vault.

2. **Application Gateway reader identity**
   - Identity: `agw-konggw-mi`
   - Client ID: `b1ff9259-2061-46b1-9940-f7e6d4987fd7`
   - Principal/Object ID: `d9c0f576-4e84-4fa5-a1e1-8b0f08ba2bae`
   - Purpose: Application Gateway reads the versionless Key Vault secret backing the certificate.

### Existing AKS identities not used directly for this certificate flow

- AKS control-plane system-assigned identity: `9be26421-0e0a-4a1f-a318-c57af73c3c4b`
- Kubelet identity client ID: `6f1d11b8-73b7-43f2-b7bc-d7face04edf1`

Do not assign Key Vault certificate permissions to the kubelet identity unless another workload explicitly needs them.

> Production recommendation: use a dedicated Workload Identity for ESO instead of reusing the CSI add-on identity. The POC below retains the working managed-identity configuration.

## 4. CSI driver clarification

The AKS Azure Key Vault CSI add-on is useful for **Key Vault to AKS** mounting and optional Kubernetes Secret synchronization. ESO PushSecret performs **AKS to Key Vault** synchronization. Therefore, the CSI add-on does not perform the PushSecret operation itself.

Enable and verify it because it is part of this POC baseline:

```bash
az aks enable-addons \
  --resource-group "$RG" \
  --name "$AKS_NAME" \
  --addons azure-keyvault-secrets-provider

az aks show \
  --resource-group "$RG" \
  --name "$AKS_NAME" \
  --query addonProfiles.azureKeyvaultSecretsProvider

kubectl get pods -n kube-system | grep -E 'secrets-store|provider-azure'
```

Expected pods include:

```text
aks-secrets-store-csi-driver-*
aks-secrets-store-provider-azure-*
```

## 5. Key Vault RBAC configuration

Confirm RBAC authorization:

```bash
az keyvault show \
  --name "$KV_NAME" \
  --resource-group "$RG" \
  --query properties.enableRbacAuthorization
```

Expected: `true`.

Set reliable resource IDs instead of depending on an empty shell variable:

```bash
KV_ID=$(az keyvault show \
  --name "$KV_NAME" \
  --resource-group "$RG" \
  --subscription "$SUBSCRIPTION_ID" \
  --query id -o tsv)

echo "$KV_ID"
```

### 5.1 ESO writer role

`PushSecret` must create and replace a Key Vault certificate. For this POC, grant `Key Vault Certificates Officer` to the AKS CSI/ESO identity:

```bash
az role assignment create \
  --subscription "$SUBSCRIPTION_ID" \
  --assignee-object-id "32a694f3-4758-47e4-b52b-5beb0cc06903" \
  --assignee-principal-type ServicePrincipal \
  --role "Key Vault Certificates Officer" \
  --scope "$KV_ID"
```

If ESO reports failure while reading or replacing the backing secret, grant `Key Vault Secrets Officer` as well:

```bash
az role assignment create \
  --subscription "$SUBSCRIPTION_ID" \
  --assignee-object-id "32a694f3-4758-47e4-b52b-5beb0cc06903" \
  --assignee-principal-type ServicePrincipal \
  --role "Key Vault Secrets Officer" \
  --scope "$KV_ID"
```

### 5.2 Application Gateway reader role

Application Gateway requires read access to the secret backing the Key Vault certificate:

```bash
az role assignment create \
  --subscription "$SUBSCRIPTION_ID" \
  --assignee-object-id "d9c0f576-4e84-4fa5-a1e1-8b0f08ba2bae" \
  --assignee-principal-type ServicePrincipal \
  --role "Key Vault Secrets User" \
  --scope "$KV_ID"
```

`Key Vault Certificate User` is optional for certificate metadata lookup, but the required runtime permission documented for Application Gateway is `Key Vault Secrets User`:

```bash
az role assignment create \
  --subscription "$SUBSCRIPTION_ID" \
  --assignee-object-id "d9c0f576-4e84-4fa5-a1e1-8b0f08ba2bae" \
  --assignee-principal-type ServicePrincipal \
  --role "Key Vault Certificate User" \
  --scope "$KV_ID"
```

Verify assignments:

```bash
az role assignment list \
  --subscription "$SUBSCRIPTION_ID" \
  --assignee-object-id "32a694f3-4758-47e4-b52b-5beb0cc06903" \
  --scope "$KV_ID" -o table

az role assignment list \
  --subscription "$SUBSCRIPTION_ID" \
  --assignee-object-id "d9c0f576-4e84-4fa5-a1e1-8b0f08ba2bae" \
  --scope "$KV_ID" -o table
```

Avoid broad roles such as `Key Vault Administrator` and subscription-level `Contributor` when the narrower roles above are sufficient.

## 10. Push the cert-manager TLS Secret to Key Vault

Save as `pushsecret.yaml`:

```yaml
apiVersion: external-secrets.io/v1alpha1
kind: PushSecret
metadata:
  name: gateway-rgs-akv
  namespace: kong
spec:
  refreshInterval: 1h
  deletionPolicy: Delete
  updatePolicy: Replace
  secretStoreRefs:
    - name: akv-cluster-secret-store
      kind: ClusterSecretStore
  selector:
    secret:
      name: gateway-rgs-tls-r
  template:
    data:
      cert.p12: '{{ fullPemToPkcs12 (index . "tls.crt") (index . "tls.key") | b64dec }}'
  data:
    - match:
        secretKey: cert.p12
        remoteRef:
          remoteKey: cert/gateway-rgs-certs
```

Explanation:

- `selector.secret.name` reads the cert-manager-managed Kubernetes TLS Secret.
- `fullPemToPkcs12` combines `tls.crt` and `tls.key` into PKCS#12/PFX.
### - `cert/` tells the Azure Key Vault provider to import a certificate, not create a plain secret.
- `updatePolicy: Replace` creates a new Key Vault certificate version when cert-manager renews the Kubernetes Secret.
- `refreshInterval: 1h` controls ESO reconciliation.
- `deletionPolicy: Delete` can delete the remote Key Vault object if the PushSecret is deleted. For production, evaluate whether `Retain` better matches recovery requirements.

Apply and force reconciliation:

```bash
kubectl apply -f pushsecret.yaml

kubectl annotate pushsecret gateway-rgs-akv \
  -n kong \
  external-secrets.io/force-sync="$(date +%s)" \
  --overwrite

kubectl get pushsecret -n kong
kubectl describe pushsecret gateway-rgs-akv -n kong
```

Verify the Key Vault certificate and backing secret:

```bash
az keyvault certificate show \
  --vault-name "$KV_NAME" \
  --name "$KV_CERT_NAME" \
  --query '{enabled:attributes.enabled,expires:attributes.expires,sid:sid,contentType:policy.secretProperties.contentType,tags:tags}'
```

Expected:

```text
enabled: true
contentType: application/x-pkcs12
sid: https://kv-kong-demo.vault.azure.net/secrets/gateway-rgs-certs/<version>
managed-by: external-secrets
```

## 11. Configure Application Gateway certificate reference using Azure CLI

The Key Vault uses RBAC, so configure the initial reference through CLI or Terraform instead of the portal.

Create the **versionless** secret ID:

```bash
CERT_SECRET_ID=$(az keyvault certificate show \
  --vault-name "$KV_NAME" \
  --name "$KV_CERT_NAME" \
  --query sid -o tsv | sed -E 's#/[^/]+$##')

echo "$CERT_SECRET_ID"
```

Expected:

```text
https://kv-kong-demo.vault.azure.net/secrets/gateway-rgs-certs
```

Create or update the Application Gateway SSL certificate reference:

```bash
az network application-gateway ssl-cert create \
  --resource-group "$RG" \
  --gateway-name "$AGW_NAME" \
  --name "$KV_CERT_NAME" \
  --key-vault-secret-id "$CERT_SECRET_ID"
```

Verify:

```bash
az network application-gateway ssl-cert show \
  --resource-group "$RG" \
  --gateway-name "$AGW_NAME" \
  --name "$KV_CERT_NAME"
```

### 11.1 Create HTTPS listener

Inspect the existing frontend names:

```bash
az network application-gateway frontend-ip list \
  --resource-group "$RG" --gateway-name "$AGW_NAME" -o table

az network application-gateway frontend-port list \
  --resource-group "$RG" --gateway-name "$AGW_NAME" -o table
```

If an HTTPS frontend port does not exist:

```bash
az network application-gateway frontend-port create \
  --resource-group "$RG" \
  --gateway-name "$AGW_NAME" \
  --name Https \
  --port 443
```

Create the listener. Replace `<FRONTEND_IP_CONFIG_NAME>` with the value returned above, for example `appGatewayFrontendIP` or `public-ipc`:

```bash
az network application-gateway http-listener create \
  --resource-group "$RG" \
  --gateway-name "$AGW_NAME" \
  --name gateway-rgs-https-listener \
  --frontend-ip <FRONTEND_IP_CONFIG_NAME> \
  --frontend-port Https \
  --ssl-cert "$KV_CERT_NAME" \
  --host-name "$DNS_NAME"
```

### 11.2 Create the routing rule

List existing backend pools and backend settings:

```bash
az network application-gateway address-pool list \
  --resource-group "$RG" --gateway-name "$AGW_NAME" -o table

az network application-gateway http-settings list \
  --resource-group "$RG" --gateway-name "$AGW_NAME" -o table
```

Create the rule using the existing Kong backend pool/settings:

```bash
az network application-gateway rule create \
  --resource-group "$RG" \
  --gateway-name "$AGW_NAME" \
  --name gateway-rgs-https-rule \
  --http-listener gateway-rgs-https-listener \
  --rule-type Basic \
  --address-pool <KONG_BACKEND_POOL_NAME> \
  --http-settings <KONG_BACKEND_HTTP_SETTINGS_NAME> \
  --priority 100
```

Use an unused priority value.

## 14. Troubleshooting

### `Identity not found` from `169.254.169.254`

Cause: the `ClusterSecretStore` uses a client ID for a managed identity unavailable to the AKS node/ESO authentication path.

Checks:

```bash
az aks show -g "$RG" -n "$AKS_NAME" \
  --query addonProfiles.azureKeyvaultSecretsProvider.identity

kubectl describe clustersecretstore akv-cluster-secret-store
kubectl logs -n external-secrets-system deployment/external-secrets --tail=200
```

For this POC, use:

```yaml
identityId: d5e0e47e-e878-4d12-b846-591b27035896
```

### `409 Conflict` while importing certificate

Cause: a plain Key Vault secret or key with the same name already exists from an earlier `remoteKey: gateway-rgs-certs` test.

```bash
az keyvault secret delete --vault-name "$KV_NAME" --name "$KV_CERT_NAME"
az keyvault secret list-deleted --vault-name "$KV_NAME" -o table
az keyvault secret purge --vault-name "$KV_NAME" --name "$KV_CERT_NAME"
```

Then reconcile PushSecret again. Purge only when reuse of the same name is intended and policy permits permanent deletion.

### Portal says Key Vault does not allow access to the managed identity

For RBAC-enabled Key Vaults, create the initial AGW certificate reference through CLI/Terraform. Verify:

```bash
az keyvault show -n "$KV_NAME" --query properties.enableRbacAuthorization
az network application-gateway show -g "$RG" -n "$AGW_NAME" --query identity
az role assignment list \
  --assignee-object-id d9c0f576-4e84-4fa5-a1e1-8b0f08ba2bae \
  --scope "$KV_ID" -o table
```

Then run the `az network application-gateway ssl-cert create` command from section 11.

### `MissingSubscription`

Cause: `$KV_ID` is empty or the CLI subscription is not selected.

```bash
az account set --subscription "$SUBSCRIPTION_ID"
KV_ID=$(az keyvault show -g "$RG" -n "$KV_NAME" --query id -o tsv)
printf 'KV_ID=%s\n' "$KV_ID"
```

### PushSecret status is `Errored`

```bash
kubectl describe pushsecret gateway-rgs-akv -n kong
kubectl describe clustersecretstore akv-cluster-secret-store
kubectl logs -n external-secrets-system deployment/external-secrets --tail=200
kubectl get secret gateway-rgs-tls-r -n kong -o jsonpath='{.type}{"\n"}'
```

Expected TLS Secret type: `kubernetes.io/tls`.

### HTTP works but HTTPS fails

```bash
kubectl describe gateway kong-gateway -n kong
kubectl get svc -n kong
kubectl get httproute -A
az network application-gateway show-backend-health -g "$RG" -n "$AGW_NAME"
openssl s_client -connect "$DNS_NAME:443" -servername "$DNS_NAME"
```

Check that the Kong service exposes port 443, the HTTPS Gateway listener has `ResolvedRefs=True`, the AGW listener uses the Key Vault certificate reference, and the routing rule points to a healthy Kong backend.

### Key Vault networking restrictions

If Key Vault networking is restricted, verify that Application Gateway can reach it. With a Key Vault private endpoint, ensure the `privatelink.vaultcore.azure.net` private DNS zone is linked to the Application Gateway VNet and resolves the vault to the private endpoint IP.

## 15. Rotation behavior

1. cert-manager renews `gateway-rgs-tls-r`.
2. ESO reconciles the PushSecret and imports a new Key Vault certificate version.
3. Application Gateway references the **versionless** backing-secret ID.
4. Application Gateway polls Key Vault for newer certificate versions and rotates the listener certificate. A configuration change to Application Gateway also triggers a Key Vault check.

Do not configure a version-specific secret ID, because it prevents automatic adoption of newer certificate versions.

---

## 16. Final security model

```text
AKS CSI/ESO identity
  -> Key Vault Certificates Officer
  -> optional Key Vault Secrets Officer if required by ESO operation
  -> writes gateway-rgs-certs

Application Gateway UAMI
  -> Key Vault Secrets User
  -> reads versionless PFX secret behind gateway-rgs-certs

Kubelet identity
  -> no certificate role for this flow

AKS control-plane identity
  -> no certificate role for this flow
```

For production, separate the ESO writer identity from the CSI add-on identity and use Azure Workload Identity with least-privilege RBAC.
